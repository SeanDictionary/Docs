# Ascend C

## AIcore架构抽象

AIcore是华为加速卡即NPU的核心计算单元。一个NPU中包含多个AIcore，类似多核CPU

AIcore中包含计算单元、存储单元和搬运单元等等。

计算单元包含三种基础计算资源：

- **Scalar** 计算单元：用于进行地址计算、循环控制等标量计算工作，并把向量计算、矩阵计算、数据搬运、同步指令发送给对应单元执行
- **Cube** 计算单元：用于进行向量计算、矩阵计算等高性能计算工作
- **Vector** 计算单元：用于进行向量计算、矩阵计算等高性能计算

搬运单元负责在 Global Memory 和 Local Memory 之间搬运数据，支持多种搬运模式。

- **MTE2**: 数据搬入单元
- **MTE3**: 数据搬出单元

存储单元在AIcore内部中统称为 Local Memory，与之相对的是 Global Memory。

**异步指令流**、**同步信号流**、**计算数据流**这三种流是AIcore中最基本的三种流。异步指令流用于发送异步指令，计算数据流用于传输计算数据，同步信号流用于传输同步信号。

## 核函数

一个核函数通常像

```c
__global__ __aicore__ void kernel_function(argument list) {
    ...
}
```

核函数必须以 void 作为返回类型，并且不能有返回值。核函数的参数列表可以包含任意数量的参数，但必须是基本数据类型或指针类型。指针变量类型同意定义为 `__gm__ uint8_t*`，为了防止过长的函数入参列表，可以使用封装的宏 `#define GM_ADDR __gm__ uint8_t* __restrict__` 来定义指针类型。

`__global__` 表示该函数是一个核函数，可以通过 `<<<...>>>` 调用; `__aicore__` 表示该函数运行在 AIcore 上。

Ascend C 中可以直接通过 `<<<...>>>` 语法来调用核函数。例如：

```c
kernel_function<<<blockDim, l2ctrl, stream>>>(argument list);
```

- blockDim: 核函数的线程块维度，表示每个线程块中线程的数量
- l2ctrl: 保留参数，暂时设置为nullptr
- stream: aclrtStream类型，应用程序通过stream任务队列来管理任务的并行

## 编程API

Ascend C 提供了一组类库API进行编程，主要包括以下几类：

- **计算类API**：提供Scalar、Vector、Matrix等计算单元的调用
- **数据搬运API**：提供MTE2、MTE3等搬运单元的调用，将数据在Global Memory和Local Memory之间搬运
- **内存管理API**：用于分配管理内存，比如AllocTensor、FreeTensor接口
- **任务同步API**：完成任务间的通信和同步，比如EnQue、DeQue接口。不同的指令异步并执行，通过向不同的组件发送同步指令，来保证指令按照正确的逻辑关系执行

4级API，API根据用户的使用场景分为4级：

- **Level 0**：可以完整发挥硬件优势的计算API，可以对任意单个数据进行计算
- **Level 1**：对多维数据中切片部分的计算
- **Level 2**：对张量内部分连续数据的计算
- **Level 3**：运算符重载，可以对整个张量计算

# 算子开发 (SIMD三段式)

## 算子交付件

一个算子交付件主要包含以下部分：

| 名称     | 说明                                                                                                                                                                             | 位置              |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| 原型文件 | 也称 Host 侧算子定义文件，负责声明算子接口、注册算子、定义算子的入口逻辑，并通常会把 Tiling、Shape/Dtype/Format 推导等逻辑挂到这个入口上。它是算子对 Host 侧框架暴露的入口文件。 | `op_host/xxx.cpp` |
| 推导文件 | 负责实现 InferShape、InferDataType 等推导函数，告诉框架输入输出的 shape、dtype、format 等属性应该如何推导，属于静态编译和图优化阶段的重要信息来源。                              | `op_proto/`       |
| 接口文件 | 定义算子对外暴露的接口规范，包括输入输出参数的名称、类型、格式、属性约束等，是算子“契约层”的描述文件，用于描述算子在框架中的调用方式。                                           | `op_api/`         |
| kernel   | 实现算子的核心计算逻辑，包含数据搬运、UB/Buffer 使用、同步、边界处理（tail）等，是真正执行算子计算的代码。                                                                       | `op_kernel/`      |

这些目录各自承担的职责可以概括为：`op_host` 负责算子注册和入口，`op_proto`/`op_api` 负责推导和接口描述，`op_tiling` 负责切分策略，`op_kernel` 负责实际计算。它们共同构成一个完整的算子交付件链路。

完整的流程涉及到如下步骤：

- 算子注册
- 算子二进制
- 文档
- Infer函数
- Tiling切分
- Kernel实现
- UT测试

完整的目录结构如下：

```
custom_op
├─── framework
├─── op_host
│    ├─── add_custom_template.cpp           // 包含算子原型注册、tiling实现 shape与Dtype推导内容
|    └─── CMakeLists.txt                    // host侧CMakeLists文件，一般不需要修改
├─── op_kernel
|    ├─── add_custom_template_tiling.h      // 算子tiling定义文件
|    ├─── add_custom_template.cpp           // 算子代码实现文件
|    └─── CMakeLists.txt                    // kernel侧CMakeLists文件，一般不需要修改
├─── CMakeLists.txt                         // 根目录CMakeLists文件，一般不需要修改
└─── build.sh                               // 编译脚本
```

## 脚手架启动

构建脚手架 msopgen 工具

需要先准备好一份 `xxx.json` 文件，里面包含算子的一些基本信息，比如算子名称、输入输出参数、数据类型等等。

```json
// xxx.json
[
  {
    "op": "AddCustomTemplate",
    "input_desc": [
      {
        "name": "x",
        "param_type": "required",
        "format": ["ND", "ND"],
        "type": ["float16", "float"]
      },
      {
        "name": "y",
        "param_type": "required",
        "format": ["ND", "ND"],
        "type": ["float16", "float"]
      }
    ],
    "output_desc": [
      {
        "name": "z",
        "param_type": "required",
        "format": ["ND", "ND"],
        "type": ["float16", "float"]
      }
    ]
  }
]
```

然后使用 msopgen 工具生成算子脚手架代码，命令如下：

```bash
msopgen gen -i xxx.json -c ai_core-ascend910b1 -lan cpp -out <custom_op_dir>
```

### tiling key

主要分为两部分，分别用来规范编译哪些 kernel 版本，并指定在 kernel 侧使用哪些 kernel 版本

```text
┌─────────────────────────────────┐
│  Part 1: DECL（声明模板参数）   │  → 编译时：告诉编译器有哪些模板参数
│  ASCENDC_TPL_ARGS_DECL(...)     │
├─────────────────────────────────┤
│  Part 2: SEL（定义合法组合）    │  → 编译时：告诉框架要编译出哪些 kernel 版本
│  ASCENDC_TPL_SEL(...)           │
└─────────────────────────────────┘
```

**参数方案容器**

ASCENDC_TPL_ARGS_DECL(算子名, 参数1, 参数2, ...)

```cpp
ASCENDC_TPL_ARGS_DECL(CustomOps,
    ...
);
```

**> 参数类型声明宏**

- 数据类型参数

ASCENDC_TPL_DATATYPE_DECL(参数名, 默认值, 绑定输入/输出)

```cpp
ASCENDC_TPL_DATATYPE_DECL(DT_X, C_DT_FLOAT, ASCENDC_TPL_INPUT(0))
```

把模板参数 `DT_X` 声明为数据类型参数，默认值为 `C_DT_FLOAT`，并绑定到输入参数 0 上。

> `C_DT_FLOAT` 是模板参数类型，具体文档查看 `asc-devkit/docs/zh/api/SIMD-API/基础API/同步控制/核内同步/TQueSync/模板参数.md`

- Format参数

ASCENDC_TPL_FORMAT_DECL(参数名, 默认值, 绑定输入/输出)

- 自定义整数参数

ASCENDC_TPL_UINT_DECL(参数名, 位宽, 取值模式, ...)

- 布尔参数

ASCENDC_TPL_BOOL_DECL(参数名, 值0, 值1)

**定义合法组合**

ASCENDC_TPL_SEL(组合1, 组合2, ...)

```cpp
ASCENDC_TPL_SEL(
    ASCENDC_TPL_ARGS_SEL(
        ASCENDC_TPL_DATATYPE_SEL(DT_X, C_DT_FLOAT),
    ),
);
```

### tiling

tiling是算子开发中非常重要的一部分，它负责将算子的计算任务划分为多个小的计算块，以便在多核 AIcore 上并行执行。tiling 的主要任务包括：

- 判断输入输出的 shape、dtype、format 是否符合算子要求。
- 根据输入输出的 shape、dtype、format 等信息，计算出每个计算块的大小和位置。
- 根据硬件资源和计算任务的特点，选择合适的 tiling 策略，以提高计算效率。
- 生成 tilingdata 结构体，包含每个计算块的相关信息，以便 kernel 在执行时使用。

先确定 TilingData 结构体所需要的字段，通常包括：

- totalNum：总共需要计算的数据量
- blockFactor：每个核总共处理的数据量
- ubFactor：每个核一次可以处理的数据量
- blockNum：计算时使用的核数

```cpp
namespace optiling {
    ...
}
```

注册 TilingData 结构体：

```cpp
BEGIN_TILING_DATA_DEF(CustomOpsTilingData)
    TILING_DATA_FIELD_DEF(uint64_t, totalNum);
    TILING_DATA_FIELD_DEF(uint64_t, blockFactor);
    TILING_DATA_FIELD_DEF(uint64_t, ubFactor);
    TILING_DATA_FIELD_DEF(uint32_t, blockNum);
END_TILING_DATA_DEF;

REGISTER_TILING_DATA_CLASS(CustomOps, CustomOpsTilingData);
```

判断输入输出的 shape、dtype、format 是否符合算子要求

获取硬件信息：

```cpp

auto platform = platform_ascendc::PlatformAscendC(context->GetPlatformInfo());
uint32_t availableCoreNum = static_cast<uint32_t>(platform.GetCoreNumAiv());
```

获取UB大小：

```cpp
uint64_t ubSize = 0;
platform.GetCoreMemSize(platform_ascendc::CoreMemType::UB, ubSize);
if (ubSize <= UB_RESERVE_BYTES) {   // UB_RESERVE_BYTES 指UB保留的大小
    return ge::GRAPH_FAILED;
}
```

计算每个AIcore一次可以处理的数据量：

```cpp
uint64_t ubFactor = AlignDown(                                      // AlignDown 按指定分割大小向下对齐
    (ubSize - UB_RESERVE_BYTES) / BYTES_PER_ELEMENT_WITH_BUFFERS,   // 一次可以处理的最大数据量
    ALIGN_FLOAT32_ELEMENTS                                          // 指定分割大小
);
```

分配核数及每个核需要计算的数据量：

```cpp
// blockNum: 计算时使用的核数
const uint64_t byBytes = std::max<uint64_t>(1UL, CeilDiv(totalNum * FLOAT32_BYTES, MIN_BYTES_PER_CORE));
const uint64_t byElems = std::max<uint64_t>(1UL, CeilDiv(totalNum, MIN_BLOCK_ELEMENTS));
// 针对数据量大小，避免小数据量的情况下仍然占用多核
const uint32_t blockNum = static_cast<uint32_t>(std::min<uint64_t>(availableCoreNum, std::min(byBytes, byElems)));

// blockFactor: 每个核总共处理的数据量
const uint64_t blockFactor = AlignUp(CeilDiv(totalNum, blockNum), ALIGN_FLOAT32_ELEMENTS);  // 按指定分割大小向上对齐
```

构造 tilingdata 结构体，并将 tilingdata 结构体拷贝到原始 tilingdata 结构体指针中：

```cpp
CustomOpsTilingData tilingData;
tilingData.totalNum = totalNum;
tilingData.blockFactor = blockFactor;
tilingData.ubFactor = ubFactor;
tilingData.blockNum = blockNum;

auto rawTilingData = context->GetRawTilingData();   // 获取原始 tilingdata 结构体指针，gert::TilingContext context
if (rawTilingData == nullptr || rawTilingData->GetCapacity() < sizeof(CustomOpsTilingData)) {   // 防止指针分配失败，或内存空间分配不足
    return ge::GRAPH_FAILED;
}
std::memcpy(rawTilingData->GetData(), &tilingData, sizeof(CustomOpsTilingData));    // 将 tilingdata 结构体拷贝到原始 tilingdata 结构体指针中，目标地址，数据地址，数据大小
rawTilingData->SetDataSize(sizeof(CustomOpsTilingData));                            // 设置结构体数据大小
```

设置使用核数：（注意区分的是，前面 tilingData 中的核数仅作为常量用于告知 kernel 计算时使用的核数，而非实际真正启用的核数

### GE

GE 是算子图引擎，主要用于算子图的构建、优化和执行。GE 提供了一组 API，用于在 Host 侧进行算子图的构建和优化。

该部分内主要实现的功能就是 Shape、Dtype、Format 的推导，以便进行静态编译和优化

```cpp
namespace ge {
    static graphStatus InferShape(gert::InferShapeContext *context)
    {
        const gert::Shape *inputShape = context->GetInputShape(0);
        if (inputShape == nullptr) {
            return GRAPH_FAILED;
        }
        gert::Shape *outputShape = context->GetOutputShape(0);
        if (outputShape == nullptr) {
            return GRAPH_FAILED;
        }
        *outputShape = *inputShape;
        return GRAPH_SUCCESS;
    }

    static graphStatus InferDataType(gert::InferDataTypeContext *context) {
        const ge::DataType inputDtype = context->GetInputDataType(0);
        context->SetOutputDataType(0, inputDtype);
        return ge::GRAPH_SUCCESS;
    }
}
```

### 成员数据

```cpp
private:
    AscendC::TPipe pipe_;               // 异步指令流，负责发送异步指令
```

### 算子初始化

```cpp

const uint64_t blockOffset = tilingData->blockFactor * AscendC::GetBlockIdx();
```

```cpp
if (blockOffset >= tilingData->totalNum) {
```

```cpp
pipe_.InitBuffer(outQueueY_, BUFFER_NUM, ubFactor_ * sizeof(DT_X));
pipe_.InitBuffer(tmpBuf_, ubFactor_ * sizeof(DT_X));
```

### 算子核心部分

作为一个算子类的对外调用的入口函数，其中包含算子核心的三个功能运行，数据搬入、计算、数据搬出

```cpp
__aicore__ inline void Process() {
    ...
}
```

按照 tilingData 中划分的参数，每次处理 ubFactor* 个数据，直到处理完 blockLength* 个数据

```cpp
if (blockLength_ == 0 || ubFactor_ == 0) {  //先做特判，防止资源占用
    return;
}
const uint64_t loopCount = ceil(blockLength_ / ubFactor_);
for (uint64_t i = 0; i < loopCount; ++i) {
    const uint64_t offset = i * ubFactor_;
    const uint64_t currentNum = min(ubFactor_, blockLength_ - offset);
    CopyIn(offset, currentNum);
    Compute(currentNum);
    CopyOut(offset, currentNum);
}
```

# 算子开发 (DAG声明式)

DAG 声明式可以看作是对手写三段式的高层封装，通过编译后将声明式写法的算子转换为手写三段式，减少开发的工作量

三段式相对 DAG 的优势是可以做手工微调，比如：

- bias 只搬入 UB 一次，多轮 ubFactor 循环中复用（DAG 不一定能优化到）
- 手动选择 Brcb（广播指令）vs DataCopy + Adds（标量加）的最优路径
- 针对非对齐 tail 做特殊 DataCopyPad 处理

# 算子开发 (SIMT直调式)

一般的数据搬运流程是 `GM -> UB -> kernel -> UB -> GM`，对于 GM 上的连续存储的数据，可以一次性搬入 UB，然后在 kernel 中反复计算再搬出。然而对于索引随机跳转、非连续存储的数据，少量多次的搬运会造成额外的性能开销，SIMT 直调式可以直接在 GM 上进行计算，减少数据搬运的开销。

   7. 修复循环达到规定上限仍未通过时，暂停并上报。
7. 泛化精度与性能验收
   1. 泛化精度验证

      6. 输出精度报告，并将结果映射到 TEST_PLAN.md 的 Case ID。
      7. 精度不达标时，回到修复与复审流程。
   2. 性能采集与分析
      1. 选定代表性性能 Case，包括主目标 case 和保护 case。
      2. 建立理论性能模型，计算预测耗时 predict_us。
      3. 在 Ascend NPU 上采集实际耗时 measured_us。
      4. 计算效率、理论开销、带宽利用、核间负载和主导瓶颈。
      5. 检查性能数据对应的被测产物是否为当前源码版本。
      6. 没有明确基线或 SLA 时，性能仅记录为“仅观测”，不能宣称绝对达标。
   3. 性能优化（仅在需要时）
      1. 根据 profiler 或理论模型定位一个明确瓶颈。
      2. 一次只做一个最小候选优化，例如切分、UB 分块、DMA、Buffer 或并行度调整。
      3. 重新执行 freshness、受影响 UT/ST/TTK 和精度验证。
      4. 对比主目标 case 的性能改善与保护 case 的性能回退。
      5. 达到接受标准则保留候选，否则回退该候选。
      6. 对最终最佳版本重新执行完整精度和性能复验。

   1. 确认最终代码位于目标仓的开发 worktree。

# 遇到的神秘问题

## Bias算子

内置 liboptiling.so 1.0 注册了 Bias 算子的旧 tiling 函数 TbeBiasTilingV3Custom，它与 ASC 2.0 注册的 TilingForBias 冲突。DoOpTilingForCompile 优先调用 1.0 接口，但 1.0 tiling 期望旧格式 compile_info（含 broadcast_bias_shape），ASC 编译器产出的是 {}，导致解析失败。

**现象**

在 Ascend950 硬件上，custom vendor 开发的 Bias 算子（V4 AscendC tiling）在 GE 在线编译通路 和 TTK dynamic compilation 通路 下，tiling 阶段失败，报错：
[bias.cc:186][OP_PROTO][TbeBiasTilingV3Custom][4069795] OpName:[Bias] "op_info_void is nullptr."
DoOpTilingForCompile: ErrorNo: 4294967295(failed) TbeOpTilingPyInterfaceOld failed.
TTK -b release（binary 模式）在隔离 fake CANN 环境（无内置 liboptiling.so）下 9/9 PASS，但在真实 active OPP 环境下同样失败。

**根因**

内置 liboptiling.so（host 侧共享库，不分 SoC 平台统一加载）中同时注册了 Bias 的 V3 legacy tiling（REGISTER_OP_TILING_V3_CUSTOM(Bias, ...)）和 V4 tiling（IMPL_OP_OPTILING(Bias).Tiling(Tiling4Bias)）。GE 加载 .so 时按 MergeFunctions 后注册覆盖先注册，内置 .so 在 custom .so 之后加载，导致内置 V3 覆盖 custom V4。
V3 的 TbeBiasTilingV3CustomParsefunc 通过 ParseJsonCompileInfo 从 kernel JSON 的 compileInfo 字段读取 legacy 字段（broadcast_bias_shape、\_ub_factor_align 等）。AscendC V4 格式的 kernel JSON 中 compileInfo: {} 为空 → V3 parse 返回 nullptr → op_info_void is nullptr → 失败。

**冲突链路**

GE 加载 tiling so:

1. custom libcust_opmaster_rt2.0.so → V4: IMPL_OP_OPTILING(Bias).Tiling(TilingForBias)
2. built-in liboptiling.so → V3: TbeBiasTilingV3Custom (REGISTER_OP_TILING_V3_CUSTOM)
   → V4: Tiling4Bias (IMPL_OP_OPTILING)
   → MergeFunctions: "op type Bias tiling func has been registered"
   → 内置 V3/V4 覆盖 custom V4

GE RunGraph → TBE 在线编译 Bias:
→ 调用内置 V3 TbeBiasTilingV3CustomParsefunc 解析 kernel JSON
→ compileInfo: {} → V3 parse 失败 → op_info_void is nullptr
→ RunGraph failed

**解决方案1**

将单算子包强制安装到built-in目录下，覆盖内置 liboptiling.so 的 Bias tiling 注册

**解决方案2**

算子改名运行

**神秘的根本原因？**

1. tiling_key.h — TilingKey 注册方式不同
旧代码（有冲突）：
ASCENDC_TPL_ARGS_DECL(Bias, ASCENDC_TPL_UINT_DECL(schMode, 8, ASCENDC_TPL_UI_LIST, ...));
ASCENDC_TPL_SEL(ASCENDC_TPL_ARGS_SEL(ASCENDC_TPL_UINT_SEL(schMode, ...)));
使用 ASCENDC_TPL_UINT_DECL — 按整数参数选模板。TilingKey 是一个 8-bit 无符号整数（schMode=0/1/2）。
新代码（无冲突）：
ASCENDC_TPL_ARGS_DECL(Bias, ASCENDC_TPL_DATATYPE_DECL(D_T_X, C_DT_FLOAT16, C_DT_FLOAT, C_DT_BF16, ASCENDC_TPL_INPUT(0)));
ASCENDC_TPL_SEL(ASCENDC_TPL_ARGS_SEL(ASCENDC_TPL_DATATYPE_SEL(D_T_X, ...)));
使用 ASCENDC_TPL_DATATYPE_DECL — 按数据类型选模板。TilingKey 基于 dtype 枚举值。

2. tiling 注册方式不同
旧代码：

```cpp
// tiling_arch35.h
#include "atvoss/broadcast/broadcast_tiling.h"
class BiasTiling : public Ops::Base::TilingBaseClass { ... };

// tiling_arch35.cpp
IMPL_OP_OPTILING(Bias).Tiling(TilingForBias).TilingParse<BiasCompileInfo>(TilingPrepareForBias);
```

使用 `Ops::Base::TilingBaseClass` + `atvoss/broadcast/broadcast_tiling.h` — ATVOSS 框架的 tiling 基类。

新代码：

```cpp
// tiling_arch35.cpp
IMPL_OP_OPTILING(Bias).Tiling(BiasTilingFunc).TilingParse<BiasCompileInfo>(TilingParseForBias);
```

直接注册 `BiasTilingFunc` — 独立的 tiling 函数，不依赖 ATVOSS 框架。

3. kernel 入口不同

旧代码：

```cpp
// bias.cpp (arch35)
GET_TILING_DATA(tilingData, tiling);  // 注意：不是 GET_TILING_DATA_WITH_STRUCT
```

kernel 入口使用 GET_TILING_DATA（不带 STRUCT），且 kernel 内部使用 `Ops::Base::BroadcastNddmaWithLoop` 等 ATVOSS broadcast 工具。

新代码：

```cpp
// bias.cpp
REGISTER_TILING_DEFAULT(BiasTilingData);
GET_TILING_DATA_WITH_STRUCT(BiasTilingData, tilingData, tiling);
```

使用 `REGISTER_TILING_DEFAULT` + `GET_TILING_DATA_WITH_STRUCT` — 自定义 TilingData 结构体。

4. TilingData 定义方式不同

旧代码：

```cpp
BEGIN_TILING_DATA_DEF(BiasTilingData)
TILING_DATA_FIELD_DEF(int64_t, blockFormer);
...
END_TILING_DATA_DEF;
REGISTER_TILING_DATA_CLASS(Bias, BiasTilingData);
```

使用 `BEGIN_TILING_DATA_DEF` / `TILING_DATA_FIELD_DEF` 宏 — CANN 框架的 TilingData 序列化。

新代码：

```cpp
struct BiasTilingData {
    int64_t totalElements = 0;
    ...
};
```

纯 C 结构体，不使用 CANN 框架的 TilingData 序列化宏。

5. compile_info 不同

旧代码的 `TilingPrepareForBias` 会写 compileInfo（coreNum、ubSize 等通过 BiasCompileInfo 传递），而 PostTiling 中 tilingData.SaveToBuffer(...) 序列化 TilingData。
新代码的 `TilingParseForBias` 基本是空的（只返回 SUCCESS），compileInfo 为空 {}。

6. 结论

旧代码冲突的根因不是"内置 V3 覆盖 custom V4"（笔记中的分析是误判），而是旧代码使用了 ATVOSS 框架的 tiling 基类和 CANN 框架的 `TilingData` 序列化宏，这些与 ASC 2.0 的 `do_op_tiling` 调用链不兼容。

具体来说：
- 旧代码用 `GET_TILING_DATA（非` WITH_STRUCT），ASC 2.0 的 `do_op_tiling` 返回的 `tiling_data` 格式与 `BEGIN_TILING_DATA_DEF` 序列化的格式不匹配
- 旧代码用 `ASCENDC_TPL_UINT_DECL，新代码用` `ASCENDC_TPL_DATATYPE_DECL` — TilingKey 计算方式不同
- 旧代码依赖 `atvoss/broadcast/broadcast_tiling.h` 的 `BroadcastTiling` 函数，新代码自己手写 tiling 逻辑

是新代码的改动（SIMD 三段式 + 自定义 `TilingData` + `DATATYPE_DECL` TilingKey）修复了兼容性问题，不是 CANN 版本变化。
